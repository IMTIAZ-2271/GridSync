## What GridSync is

Postgres-backed app that bills two-way electricity flow between solar homes and
the grid. Ingests 30-minute interval readings, runs Time-of-Use billing in
strict SQL transactions, tracks net energy balance and monthly credit rollover.

Portfolio project. Repo: github.com/IMTIAZ-2271/GridSync. Local: E:\Codes\GridSync

### Billing engine — `db/sql/billing.sql`

`run_billing(p_site_id uuid, p_period_start date) RETURNS uuid`.
One transaction, FOR UPDATE on billing_period, idempotent via UNIQUE(period_id).
Produces 16 bills across 8 sites x 2 complete months, 168 line items,
15 ledger entries. Rule 8 correctly refuses the two partial months.

Verified behaviour: solar sites earn credit in June, June's credit fully covers
July's bill. Non-solar sites pay ~60% more.

### Onboarding — `db/sql/backfill.sql`, 5 new API endpoints, wizard UI

`backfill_readings(device_id, from, to, capacity_kw DEFAULT NULL) RETURNS
integer` — same consumption/solar profile as `seed_demo.sql`, extracted so
both share one curve. `meter` devices get import/export netted against the
solar curve; `inverter` devices get generation only. **Upserts** on
`(device_id, interval_start)` rather than skipping conflicts: `POST
/api/sites/{id}/solar` registers the inverter/array/agreement, backfills the
inverter, then **re-runs this same call against the billing meter** now that
capacity is known. Without that re-net, a site's meter — backfilled by
`/meter` before any solar existed, `capacity_kw = NULL` — would show zero
export forever, so it would never earn or roll over credit, which is the
entire feature this project exists to demonstrate. Fixed after initial
onboarding review caught it live.

Any interval whose `billing_period` is already `frozen`/`billed`/`closed` is
excluded from the upsert regardless (rule 8) — enforced inside the function
itself, because `reading_period_open_guard` (the trigger that's supposed to
own this) doesn't exist; see Deferred deliberately, below.

New endpoints, all consumer-scoped: `GET /api/tariff-plans`, `POST
/api/sites`, `POST /api/sites/{id}/meter`, `POST /api/sites/{id}/solar`,
`POST /api/sites/{id}/bill` (loops every complete month via `run_billing`
under `REPEATABLE READ` with retry on `40001`; the rule-8 coverage gate is
treated as skip-this-month, not fail-the-request). Registering with an empty
`meter_serial` now creates the account with no site instead of 404ing.

Frontend: 3-step wizard (site → meter → solar, skippable) in
`CustomerOnboarding.tsx`, rendered by `CustomerOverview` when the signed-in
customer owns no sites. Finishing screen shows a per-step checklist with a
simulated progress bar during each ~4,300-row backfill (there is no real
progress to report — one request per step — so it creeps toward ~92% and the
checkmark, not the bar, signals completion).

Verified end-to-end over live HTTP, twice (once before the export-netting
fix, once after): a freshly onboarded solar site now shows nonzero export,
earns credit in month 1 (`amount_due > 0`, `credit_opening_kwh = 0`), and
applies that credit in month 2 (`credit_opening_kwh` = month 1's earned kWh,
`amount_due → 0.0000`) — same shape as Seed Site 01's June/July bills.

### Deferred deliberately
- `reading_role_guard` (rule 6) — device-type-appropriate reading validation
- `reading_period_open_guard` (rule 8) — divert late readings at insert time;
  currently enforced in run_billing only
- `services/ingest/` — HTTP ingest endpoint, never built (seed writes directly)
- `services/jobs/` — scheduled billing, rollups, partition pre-creation
- site_daily_summary and site_monthly_summary exist but nothing populates them
- Prepaid metering and recharge — out of scope
- Applications/approvals workflow upstream of net_metering_agreement

### Known weaknesses (state these honestly, don't hide them)
- No token revocation — a suspended account works until expiry
- No rate limiting or lockout on login
- localStorage is XSS-readable (httpOnly cookies would be better)
- Government/supplier registration codes are shared secrets, no rotation
- No automated API or auth tests
- `/api/issues` returns all issues and the customer page filters client-side
- `reading_period_open_guard` (rule 8) still doesn't exist as a trigger.
  `backfill_readings()` enforces the billed/frozen boundary itself for its
  own upserts (see Onboarding, above), but no other write path to
  `device_reading` is protected — `docs/erd-logical.md` documents the trigger
  as if it were built; it never was
- `seed_demo.sql` keeps its own copy of the consumption/solar curve rather
  than calling `backfill_readings()` — deliberately not refactored, to avoid
  changing the seeded demo dataset's committed numbers for an unrelated task
- Local dev DB (`gridsync`) has ~6 leftover test accounts/sites from
  verifying onboarding (`onboard-smoke*`, `browser-test-onboard`,
  `fixtest`, `fix-verify-*`) — harmless, but not cleaned up: their bills are
  append-only, so removal needs disabling the `*_immutable` triggers, which
  auto-mode correctly refused to do unattended. `pytest` currently shows 1
  failure as a result —
  `test_telemetry_partitioning.py::test_same_interval_on_a_different_device_is_fine`
  does an unscoped `COUNT(*)` on `device_reading` for one timestamp, which
  now also counts leftover backfilled rows landing on the same moment. Test
  fragility exposed by this data, not caused by it — worth scoping that
  query to the devices it creates

## The eight non-negotiable rules

Full rationale in `docs/decisions.md`. Summary:

1. Money is immutable — bills never UPDATEd, rates versioned, ledger append-only
2. Snapshot don't join for anything historical
3. Bill the site, not the device
4. Idempotency by constraint, not by code
5. NUMERIC everywhere — money (14,4), energy (12,4), rates (10,6). Never FLOAT
6. Export measured at the meter, never the inverter
7. Exactly one device per site has `billing_role = 'billing'`
8. Never bill an incomplete period (coverage_pct gate)
